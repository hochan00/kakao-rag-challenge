## [생성 모델] 7B 양자화 방식 — bitsandbytes(NF4) 채택, GPTQ 경로는 폐기

**상황:** T4(16GB)에서 Qwen2.5-7B-Instruct를 돌리려면 4bit 양자화가 필요하다. 두 방식을 검토: ① `Qwen2.5-7B-Instruct-GPTQ-Int4` 사전 양자화 체크포인트(`auto-gptq`/`gptqmodel` + `optimum` 필요) ② fp16 원본 + `bitsandbytes`로 로드 시점 4bit 양자화.

**시도 순서 (전부 Colab T4에서 실측):**
1. GPTQ-Int4 + `auto-gptq` → `pip install` 단계에서 `CalledProcessError`. (stderr 미확보. auto-gptq가 Colab의 torch/CUDA에 맞는 prebuilt wheel이 없어 소스 빌드하다 실패하는 흔한 패턴으로 추정)
2. bitsandbytes(NF4) → **설치·로딩 모두 정상.** 다만 fp16 원본 ~15.2GB를 받아야 함.
3. GPTQ-Int4 + `gptqmodel` → 설치 시 pip이 numpy를 교체해 세션이 깨짐(`ImportError: cannot import name '_center'`). `docs/TROUBLESHOOTING.md` 참고.
4. 3번에 `numpy==2.0.2`(Colab 기본값) 고정 추가 → numpy 문제는 해소됐고 임베딩 단계까지 정상 진행. 그러나 `optimum`이 없어 실패.
5. 4번에 `optimum` 추가 → **최종 실패.** `optimum`은 `gptqmodel>=7.0.0`을 요구하는데, numpy를 2.0.2에 고정한 탓에 pip이 numpy를 맞추느라 `gptqmodel 2.2.0`으로 내려가 버렸다. 세 요구(optimum ↔ gptqmodel 7.x ↔ numpy 2.0.2)가 동시에 성립하지 않는다.

**결정:** **bitsandbytes(NF4) 채택.** fp16 원본을 받아 로드 시점에 4bit 양자화한다. numpy는 일부러 핀을 걸지 않되(핀이 다른 패키지를 옛 버전으로 끌어내리는 게 5번의 실패 원인이었다), 설치 후 numpy가 바뀌지 않았는지 검사해 바뀌면 즉시 명확한 에러로 중단시킨다.

**이유:**
- **GPTQ 경로는 의존성이 서로 모순되어 막혔다** (위 5번). Colab 환경에서 해소할 방법을 찾지 못했다.
- **다운로드 용량은 애초에 문제가 아니었다.** 운영진 확인 결과 **채점 대상은 문항당 `/answer` 응답 시간(120초 제한)뿐이고, 모델 다운로드·로딩 시간은 무관**하다. 다운로드는 1번 셀에서 일어나므로 측정되지 않는다. 처음에 이걸 핵심 병목으로 보고 GPTQ를 선택했던 판단은 **전제가 틀렸다.**
- 참고로 관측된 다운로드 속도 편차가 커서(7.98 ~ 80.8MB/s) 15.2GB 소요 시간 추정도 크게 흔들렸는데, 위 사실로 이 논점 자체가 무의미해졌다.
- **탈락한 대안(GPTQ-Int4):** 보정 데이터셋 기반이라 이론상 품질이 약간 유리할 수 있으나, Colab에서 설치 자체가 불가능해 검증할 수 없었다.

**남은 확인 사항:** bitsandbytes NF4의 품질이 3B 대비 실제로 나은지는 자체 평가셋으로 측정해야 한다(`docs/result/experiments.md`). → **아래 "3B → 7B 채택"에서 측정 완료.** 3B 기준선은 `docs/result/result_generator_1.ipynb`.

## [생성 모델] 3B → 7B 채택

**상황:** 동일 파이프라인에서 생성 모델 크기만 바꿔 1·2회차 A/B 비교를 진행했다. 두 노트북의 차이는 `GENERATION_MODEL` 한 줄뿐이며(diff로 검증), 임베딩·검색·청킹·프롬프트·양자화 설정·공통 러너가 모두 동일하다.

**결정:** **Qwen2.5-7B-Instruct(bitsandbytes NF4) 채택.**

| 회차 | 모델 | MRR | keyfact F1 | judge | 총점 |
| --- | --- | --- | --- | --- | --- |
| 1 | 3B | 1.0000 | 0.6006 | 90.95 | 83.494 |
| 2 | **7B** | 1.0000 | **0.7275** | **95.35** | **89.5** |

**이유:**
- **총점 +6.0점.** keyfact F1 +0.127, judge +4.4로 두 축이 함께 올랐다.
- **MRR이 양쪽 다 정확히 1.0**으로 나와 검색 코드가 동일하게 동작했음이 검증됐다. 따라서 점수 차이는 순수한 생성 모델 효과로 귀속할 수 있다.
- 문항당 120초 제한 내에서 동작하므로 속도상 불이익이 없다. 다운로드·로딩 시간은 채점 대상이 아니다(위 항목 참고).

## [데이터] 항 단위 키팩트 사전 생성

**상황:** 2회차 기준으로 남은 점수 여지가 **MRR 0점 / keyfact 8.17점 / judge 2.33점**이다. 개선 여지가 사실상 생성 쪽에만 있고, 그 주 실패 모드는 **키팩트 누락**이다 — P08은 정답 키팩트 2개 중 1개만, P07은 3개 중 2개만, P02는 2개 중 1개만 담았다. judge 4축 중 completeness가 8.8로 최저인 것도 같은 원인을 가리킨다.

**결정:** 229개 **항(unit)마다** 키팩트를 오프라인으로 사전 생성해 생성 프롬프트에 함께 투입한다. **검색에는 사용하지 않는다**(임베딩에 미포함).

**이유:**
- **정답 키팩트는 원문의 재구성이지 새 내용이 아니다.** P03 실측 결과 각 키팩트가 원문 토큰을 **88~100% 그대로** 사용한다. 따라서 공개 10문항을 few-shot 예시로 주면 스타일 재현이 가능하다.
- **조 단위로 만들면 안 된다.** 공개 키팩트는 질문에 맞춰 잘라낸 부분집합이다. P03 키팩트는 제7조 ①항(서비스 5가지)만 다루고 ②항(광고성 정보 사전동의)은 한 줄도 없다. 조 단위로 이 범위를 흉내 내면 비공개 문항이 ②항을 물을 때 무용지물이 된다. **항 단위로 만들면 검색이 이미 항을 고르므로 질문별 선별이 자동으로 이루어진다.**
- **검색에 넣지 않는 이유**는 MRR이 이미 1.0이라 개선 여지가 0이고 회귀 위험만 있기 때문이다.

**규정 검토:** 외부 상위 LLM으로 오프라인 사전 생성하는 방식이다. 금지 조항("외부 생성형 LLM API")은 런타임 대상으로 해석했고, 약관 데이터 준비 방식은 팀별 자유라는 운영진 답변이 있다(`docs/common/discord-questions.md`). 실행 중에는 Qwen만 사용한다. 다만 해석 여지가 있으므로 Discord 확인을 권장한다.

**추출 사양:**

| 항목 | 기준 |
| --- | --- |
| 단위 | 229개 항 각각 (조 단위 아님) |
| 범위 | 해당 항의 **모든 내용을 빠짐없이** 덮는다. 공개 예시의 "질문에 맞춘 좁은 범위"를 흉내 내지 않는다 |
| 표현 | 원문 어휘·수치·조건을 **그대로 보존**. 요약·패러프레이즈 금지 — 토큰 겹침이 점수이므로 바꿔 쓰면 손해 |
| 형식 | 주어가 복원된 **독립 완성 문장** (`1.통합로그인 : …이용할 수 있습니다` → `통합로그인은 …서비스입니다`) |
| 열거형 항 | 항목을 모은 요약 문장을 하나 추가 (P03 키팩트 1이 이 패턴, 원문 토큰 커버율 100%) |
| few-shot | 공개 10문항 정답 키팩트를 예시로 제공하되 **스타일만** 차용하고 범위는 항 전체로 확장 |

## [프롬프트] 근거 전달 단위를 조 전문에서 항으로 (제안 — 팀 협의 필요)

### 무엇이 문제인가

검색은 **항(unit) 229개** 단위로 정밀하게 하는데, 프롬프트에는 **조(article) 전문**이 들어간다. 검색이 알아낸 "어느 항이 맞았는지"가 생성 단계로 전달되지 않고 버려진다.

`src/indexing/retrieve.py:22-26`에서 항 점수를 조로 뭉갤 때 최댓값만 남기고 **어느 항이 그 점수를 냈는지(argmax)를 버린다**:

```python
def _aggregate(unit_scores, parents, n_articles):
    scores = np.full(n_articles, -np.inf)
    np.maximum.at(scores, parents, unit_scores)   # ← max만 취하고 argmax는 소실
    return scores
```

그 결과 `src/indexing/retrieve.py:76`이 조 객체를 그대로 돌려주고,

```python
return [self.articles[i] for i in ranked]
```

`src/indexing/notebook_impl.py:172-173`이 조 전문(`a["text"]`)을 프롬프트에 넣는다:

```python
evidence = "\n\n".join(
    f"[S{i}] {a['citation']}\n{a['text']}" for i, a in enumerate(candidates, 1)
)
```

**구체적 피해:** 카카오계정 약관 제7조는 ①항(서비스 5가지)과 ②항(광고성 정보 사전 수신동의)으로 구성된 695자다. 질문이 ①항만 물어도 ②항이 함께 투입된다. 더 심한 경우 제10조는 항이 7개인데 P01은 그중 ②항 하나만 필요하다 — **나머지 6개 항이 전부 노이즈**로 들어간다. 조 4개를 넣으므로 프롬프트 전체로는 수천 자 규모이고, 상당 부분이 질문과 무관하다.

**측정된 결과:** 2회차의 주 실패 모드가 **정답 키팩트 일부 누락**이다. P08은 2개 중 1개만(F1 0.4286), P07은 3개 중 2개만(0.4390), P02는 2개 중 1개만(0.6111) 담았다. judge 4축 중 completeness가 8.8로 최저인 것도 같은 원인이다. keyfact F1에서만 8.17점을 잃고 있다.

### 어떻게 바꾸는가

**설계 원칙: `retrieved` 반환값은 한 글자도 바꾸지 않는다.** 조 순위 계산 로직을 그대로 두면 출력이 2회차와 완전히 동일해져 **MRR 1.0이 보장되고 A/B 통제가 유지**된다. 프롬프트에 들어가는 내용만 바꾼다.

**① `src/indexing/retrieve.py:22-26` — `_aggregate()`에 argmax 반환 추가**

현재는 조별 최고 점수만 반환한다. **조별로 어느 항이 몇 점이었는지**를 함께 돌려주도록 바꾼다. 기존 반환값(조 점수 배열)의 형태와 의미는 유지해서 `_sparse_article_scores`(43-46행)·`_dense_article_scores`(48-50행)의 기존 호출이 깨지지 않게 한다.

**② `src/indexing/retrieve.py:68-76` — `retrieve()`가 항 정보를 함께 반환**

지금은 `self.articles[i]`(조 dict)만 반환한다. 여기에 **그 조에서 점수가 높은 상위 N개 항**을 실어 보낸다. 조의 순서와 개수는 그대로 유지한다 — `retrieved` 계약에 영향을 주면 안 된다.

```
반환 예시 (조 순서·개수 불변, 항 정보만 추가)
[
  { ...기존 article 필드 그대로...,
    "top_units": [ {order: 1, text: "①...", key_facts: [...]},
                   {order: 2, text: "②...", key_facts: [...]} ] },
  ...
]
```

- 조당 항 개수 `N`은 **3**을 제안한다(근거는 아래 별도 항목)
- **항 순위는 이미 계산된 항 원점수(sparse 또는 dense)로 정렬해 상위 N개를 고른다.** 조 단위 RRF 점수는 항에 존재하지 않으므로 쓸 수 없다. 별도의 융합 방식을 설계할 필요는 없다 — 아래 이유로 영향 범위가 작다

> **정렬 방식에 시간을 쓸 필요가 없는 이유:** 조 72개 중 **49개(68%)가 항 3개 이하**여서 N=3이면 전부 포함된다. 순위가 실제로 결과를 가르는 건 항 4개 이상인 **23개 조(32%)**뿐이고, 그중 다수도 4~5개 중 3개를 고르는 수준이다. 정교한 sparse·dense 융합을 설계해도 얻는 게 적다. 신경 쓰이면 나중에 실험 항목으로 분리해 확인한다.
>
> 참고로 항 원점수 자체의 변별력은 충분하다 — P01 질문에서 제10조 항별 sparse 점수는 정답인 ②항이 0.6947로 1위, 나머지 6개는 0.28~0.39였다.

**③ `src/indexing/notebook_impl.py:172-173` — `evidence` 구성 변경**

조 전문(`a["text"]`) 대신 **선별된 항의 텍스트**를 넣는다. `citation`은 조 단위 그대로 유지해야 모델이 근거를 `[S1]` 형태로 지목하는 기존 파싱(`_parse_generation`, 197-207행)이 계속 동작한다.

**④ 노트북 재생성**

`src/indexing/*`는 노트북의 원본이다. 수정 후 `notebook_payload.py`/`build.py` 경로로 **노트북 1번 셀을 다시 생성**해야 반영된다. 스냅샷 자체(`TERMS_SNAPSHOT_B64`, SHA256)는 데이터가 안 바뀌므로 그대로다.

**⑤ 테스트**

`tests/test_retrieve.py`가 `HybridRetriever`를 직접 쓴다. `retrieve()` 반환 구조가 바뀌므로 이 테스트를 함께 갱신한다. **MRR이 1.0을 유지하는지**를 회귀 테스트로 고정해두면, 이후 변경에서 검색이 깨지는 걸 자동으로 잡을 수 있다.

### 건드리지 않을 것

| 대상 | 이유 |
| --- | --- |
| `rank()` (`retrieve.py:52-66`) | 조 순위 산출. 여기를 바꾸면 `retrieved`가 달라져 MRR 통제가 깨진다 |
| `_rrf()` (`retrieve.py:13-19`), `RRF_K`, `CANDIDATE_DEPTH` | 검색 순위 결정 요소. MRR 1.0이라 개선 여지 0, 회귀 위험만 있다 |

| `answer_question()`의 `retrieved` 조립 (`notebook_impl.py:242`) | 반환 계약 |

### 검증 방법

수정 후 **`retrieved` 출력이 2회차와 완전히 동일한지** 먼저 확인한다. `docs/result/answers_public_14_2.json`의 각 문항 `retrieved` 배열과 대조해서 하나라도 다르면 조 순위 로직이 오염된 것이므로 되돌린다. 동일하다면 프롬프트만 바뀐 것이 보장되므로, 이후 점수 변화는 전부 생성 쪽 효과로 귀속할 수 있다.

**협의 필요:** 검색기는 팀원 담당 영역이므로 구현 전 조율한다.

## [프롬프트] 조당 전달 항 개수 3개 (제안 — 팀 협의 필요)

**상황:** 항 단위로 좁힐 때 조당 몇 개를 넣을지 정해야 한다.

**제안:** **조당 상위 3개 항.**

**이유:** 공개 10문항의 정답 키팩트가 몇 개 항에 걸치는지 실측했다.

| 유형 | 문항 | 비율 |
| --- | --- | --- |
| 단일 항에서 전부 도출 | P01·P02·P03·P04·P05·P07·P08·P09 | 8/10 |
| **복수 항에 걸침** | **P06(2개 항), P10(3개 항)** | **2/10** |

- 항을 1개만 넣으면 **20% 확률로 키팩트를 구조적으로 놓친다.**
- 전부 넣으면 현재와 같아진다(P01은 제10조 항 7개 중 1개만 필요).
- 3개면 확인된 케이스를 모두 덮으면서 노이즈를 크게 줄인다. 다만 비공개 30문항에 4개 항짜리가 나올 가능성은 남는다.

**협의 필요:** 위 항목과 함께 결정한다.
