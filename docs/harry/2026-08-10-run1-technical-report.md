## 1. 원문 인덱싱

### 1.1 대상 데이터

| 문서명 | 시행일 | 조 | 항 | 원문 SHA-256 |
| --- | --- | ---: | ---: | --- |
| 카카오계정 약관 | 2026-05-29 | 17 | 47 | `38510776d7bf…` |
| 카카오 위치정보 이용약관 | 2026-07-16 | 16 | 43 | `43c357f899df…` |
| 카카오 통합서비스약관 | 2026-05-29 | 18 | 63 | `f3d9c6341dbd…` |
| 카카오 통합 약관 (아카이브) | 2022-08-25 | 21 | 76 | `fa97d8138cde…` |
| **합계** | | **72** | **229** | 본문 47,733자 |

47,733자는 A4 25쪽 수준이다. **이 규모가 이후 모든 결정을 지배한다** — 인덱싱 비용이 전부 무시 가능하므로 "빠른 근사" 대신 "느려도 정확"을 일관되게 택했다.

### 1.2 파싱: 문서별 규칙 분기

네 문서는 겉보기와 달리 **"3+1" 구조**다. 통합 약관(2022 아카이브)만 표기 체계가 완전히 다르다.

| 문서 | 조 헤더 | 항 마커 | 호 마커 |
| --- | --- | --- | --- |
| 계정 / 위치정보 / 통합서비스 | `제 1 조 (목적)` 공백O 괄호O | `①`~`⑳` | `N.` |
| **통합 약관** | `제1조 목적` 공백X 괄호X | **`N.`** | 마커 없음 |

**가장 중요한 파싱 결정:** 같은 `N.` 마커가 문서에 따라 항이거나 호다. 단일 규칙으로 통일하면 청크 계층이 무너진다. 계정 약관 제12조는 `①…아래 각 호의 행위는` 뒤에 `1.` `2.`…가 붙는 항-호 구조지만, 통합 약관 제10조는 `1.` `2.`…가 곧 항이다.

조 헤더 정규식은 두 표기를 `\s*`로 흡수하고, **줄 전체 매칭**(`^…$`)이라 본문 중 상호참조(`제14조 제1항에 따라…`)는 자동 배제된다.

```python
ART = re.compile(r"^제\s*(\d+)\s*조\s*[\(（]?\s*([^)）]*?)\s*[\)）]?\s*$")
HEAD = {"circled": r"^[①-⑳]", "numdot": r"^\d+\."}   # 문서별 선택
```

**마커 없는 줄은 직전 항에 붙인다.** 통합 약관 제11조 4항(유료서비스 환불)은 `4.` 아래에 마커 없는 규정 줄이 이어지는데, 이를 떼면 "무슨 환불인지" 문맥을 잃는다.

### 1.3 정규화: 검색에만 영향, 의미는 불변

| 하는 것 | 하지 않는 것 |
| --- | --- |
| 유니코드 NFC 통일 | 숫자 표기 변경 |
| 곡선 따옴표 `‘’“”` → `'` `"` | 조사 분리 |
| 중점 `・`(U+30FB) → `·`(U+00B7) | 괄호 제거 |
| 연속 공백 축약, 웹 UI 잔여 문구 제거 | 띄어쓰기 교정 |

`제16조 제2항`, `6개월`, `2시간` 같은 토큰이 **그대로 남아야** 희소 검색이 P02·P05를 잡는다. 중점 정규화는 위치정보 약관의 `수집·이용·제공` 매칭에 직접 영향을 준다(15회 등장).

### 1.4 청킹: small-to-big 두 층

```
조(article) 72개  ← 검색 점수 집계 단위, 인용 단위, LLM 근거 단위
  └ 항(unit) 229개 ← 임베딩·희소 인덱싱 단위
```

**왜 두 층인가.** 제출 계약의 `retrieved`가 `[문서명, 조번호]`뿐이라 **인용 단위는 조로 고정**된다. 그런데 조 길이는 p90 1,529자 / 최대 3,482자로, 512토큰 모델에 통째로 안 들어간다. 반대로 항을 인용 단위로 쓰면 계약에 항 번호를 담을 자리가 없다.

| 지표 | 조 | 항 |
| --- | ---: | ---: |
| p50 | 549자 | 157자 |
| p90 / p95 | 1,529자 | 527자 |
| max | 3,482자 | 1,812자 |

**금지행위 열거 조항은 호를 쪼개지 않는다.** 항목 하나만 검색되면 무슨 목록인지 알 수 없기 때문이다.

### 1.5 검증 게이트 — 통과 못 하면 인덱싱 중단

| 검사 | 기대값 | 결과 |
| --- | --- | --- |
| 조 수 | 17 / 16 / 18 / 21 = 72 | ✅ |
| 항 수 | 47 / 43 / 63 / 76 = 229 | ✅ |
| 조 번호 연속성 | 각 문서 `1..N` 빈틈 없음 | ✅ |
| 청킹 무손실 | 항을 합치면 조 본문 완전 복원 (72/72) | ✅ |
| 골드 커버리지 | 공개 골드 12쌍 전부 존재 | ✅ |
| 시행일 | 푸터 파싱값 = 상수 | ✅ |
| 원문 해시 | 4개 파일 SHA-256 기록 | ✅ |

이 게이트는 노트북 1번 셀에서도 **재실행된다.** 내장 스냅샷을 풀 때 SHA-256과 조·항 수를 다시 확인하고, 어긋나면 즉시 중단한다.

## 2. 데이터의 결정적 특성: 문서 간 중복 조항

문자 3-gram Jaccard > 0.4인 **문서 간 조문 쌍이 30건**이다.

| 유사도 | 조문 A | 조문 B |
| ---: | --- | --- |
| **0.97** | 카카오계정 약관 제14조(회원에 대한 통지 및 공지) | 카카오 통합서비스약관 제17조(통지 및 공지) |
| 0.91 | 카카오계정 약관 제13조(개인정보의 보호) | 카카오 통합 약관 제15조(개인정보의 보호) |
| 0.89 | 카카오계정 약관 제17조(분쟁의 해결) | 카카오 통합서비스약관 제18조(분쟁의 해결) |

**공개 골드셋이 이 구조를 정면으로 겨냥한다.**

- **P02**: 같은 사실("2시간 이상 지연 시 공지")이 3개 문서에 있고 **셋 다 정답** → 문서 다양성을 유지해야 함
- **P08 (trap)**: `제3조 약관 외 준칙`은 네 문서 모두에 있는데 **통합 약관 것만 정답** → 문서를 특정해야 함

두 요구가 정반대다. 하드 필터링하면 P02를 놓치고, 아무 신호도 안 주면 P08을 틀린다.

**대응:** 모든 임베딩 청크 본문 앞에 문서명과 조 제목을 붙인다.

```python
embed_text = f"{doc_name} 제{article}조({article_title})\n{unit_text}"
```

본문만 임베딩하면 유사도 0.97짜리 두 조문의 벡터가 사실상 구분되지 않는다. 접두어가 붙으면 `위치정보`·`Daum`·`통합서비스` 같은 **문서 고유 어휘가 벡터에 들어가** 순위가 갈린다. 필터가 아니라 신호이므로 P02의 다중 정답도 살아남는다.

## 3. 임베딩 모델과 저장

### 3.1 모델 선택: 성능이 아니라 무손실로 결정

| 후보 | 파라미터 | 차원 | 컨텍스트 | 절단 청크 | hit@1 | MRR |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| `intfloat/multilingual-e5-base` | 278M | 768 | 512 | **2개** | 0.90 | 0.95 |
| **`BAAI/bge-m3`** ✅ | 568M | 1024 | 8192 | **0개** | 1.00 | 1.00 |

e5-base가 자른 2개 청크:
- 617토큰 → `카카오계정 약관 제12조(회원의 의무)`
- 888토큰 → `카카오 통합서비스약관 제12조(통합서비스 이용 방법 및 주의점)`

**확정 근거는 절단 게이트 하나다.** 지표 차이(hit@1 0.9→1.0)는 **1문항**이며, 공개 10문항은 희소 검색 단독으로도 hit@3 = 1.00인 **천장 상태**라 모델 우열의 근거가 되지 못한다. 반면 절단은 표본 크기와 무관한 결정론적 사실이다.

8192 컨텍스트의 부수 이득: **2차 분할 로직 자체가 사라진다.** 512토큰 모델을 쓰면 초과 청크를 문장 경계로 나누는 코드, 분할 청크의 부모 재매핑, 경계에서 잘린 문맥 처리가 전부 따라붙는다. 큰 모델을 고르는 것이 코드를 줄였다.

재현성을 위해 Hugging Face revision을 고정했다: `5617a9f61b028005a4858fdac845db406aefb181`

### 3.2 저장: 벡터 DB를 쓰지 않는다

| 구분 | 값 |
| --- | --- |
| 벡터 수 | 229 |
| 차원 | 1024 |
| 밀집 행렬 | 229 × 1024 × 4B = **0.94MB** |
| 질의당 연산 | `(1,1024) @ (1024,229)` = 23만 FLOP |

L2 정규화한 numpy 행렬에 행렬곱 한 번이면 **229개 전체에 대한 정확한 cosine 유사도**가 나온다.

FAISS·Chroma·Qdrant를 배제한 이유 셋:

1. **ANN이 해결하는 문제가 없다.** HNSW/IVF는 전수 비교가 감당 안 되는 10만~100만 벡터에서 정확도를 조금 버리고 속도를 얻는 기법이다. 229개에서는 정확도만 버린다.
2. **제출물이 노트북 1개다.** 외부 DB 파일이나 영속 디렉터리를 둘 자리가 없다.
3. **의존성이 실패 지점이다.** `faiss-cpu` 설치 실패나 버전 불일치는 새 Colab 런타임에서 실제로 일어난다.

임베딩을 미리 계산해 노트북에 넣지도 않았다. **질의 인코딩에 어차피 모델이 필요**하므로, 모델이 메모리에 있으면 229청크 인코딩은 몇 초짜리 초기화 비용에 불과하다.

## 4. 검색기

### 4.1 두 검색기를 쓰는 이유

| 질문 | 결정적 토큰 | 밀집 단독 위험 |
| --- | --- | --- |
| P02 | `2시간` | 숫자가 벡터에서 희석됨 |
| P05 | `제16조 제2항`, `6개월` | 법령 인용은 위치정보 약관에만 4건 |
| P07 | `카카오 T택시` | 고유명사, 통합약관에 영문 54건 |

**희소:** `TfidfVectorizer(analyzer="char_wb", ngram_range=(2,5), sublinear_tf=True)`

문자 n-gram을 쓴 이유는 **형태소 분석기(kiwi, mecab) 설치 없이** 한국어 조사 변형을 흡수하기 위해서다. `보관합니다` / `보관하나요` / `보관`이 모두 부분 매칭된다. 새 Colab에서 형태소 분석기 설치가 실패할 위험도 함께 제거된다.

### 4.2 Reciprocal Rank Fusion (RRF)

두 검색기의 **점수 스케일이 다르므로** 점수를 직접 더할 수 없다(TF-IDF cosine과 bge-m3 cosine은 분포가 다르다). RRF는 점수 대신 **순위만** 쓴다.

```
score(조) = Σ  1 / (k + rank + 1)        k = 60, 상위 8개만 참여
        검색기별
```

- **k = 60** — 상위 순위 가중을 완만하게 하는 표준값. 1위와 2위의 격차를 과장하지 않는다
- **depth = 8** — 각 검색기에서 상위 8개 조만 융합에 참여. 꼬리 잡음 차단
- **동점 처리** — RRF가 같으면 밀집 점수로 가른다(`np.lexsort`). 두 검색기 모두 상위에 못 올린 조는 융합 점수 0이므로 밀집 순으로 뒤에 붙는다

### 4.3 부모 조 집계: max, 평균 아님

같은 조에 속한 항 청크들의 점수 중 **최댓값**을 그 조의 점수로 삼는다.

**평균을 쓰면 길이가 곧 페널티가 된다.** 긴 조문일수록 질문과 무관한 항을 많이 갖기 때문이다. P09의 정답 `카카오 통합 약관 제10조`는 1,385자짜리 긴 조문이라 평균 집계에서 불리해진다.

```python
scores = np.full(n_articles, -np.inf)
np.maximum.at(scores, parents, unit_scores)   # 항 → 부모 조 max
```

### 4.4 검색 결과 (공개 10문항)

| 방식 | hit@1 | hit@3 | all-gold R@4 | MRR |
| --- | ---: | ---: | ---: | ---: |
| 희소 단독 | 0.90 | 1.00 | 1.00 | 0.950 |
| 밀집 단독 | 1.00 | 1.00 | 1.00 | 1.000 |
| **하이브리드 RRF** | **1.00** | 1.00 | **1.00** | **1.000** |

10문항 전부 정답 조문이 1위. P02의 3개 정답도 상위 3위 안에 모두 회수.

**해석 주의:** 희소 단독으로도 hit@3 = 1.00이다. **공개셋은 세 방식을 구분하지 못한다.** 하이브리드를 채택한 근거는 이 표가 아니라 §4.1의 질의 유형 분석이다 — 비공개 30문항에 숫자·법령 인용이 더 나올 때를 대비한 보험이다.

## 5. 생성

### 5.1 모델

| 항목 | 값 |
| --- | --- |
| 모델 | `Qwen/Qwen2.5-3B-Instruct` (규정상 Qwen2.5-Instruct 계열 필수) |
| 양자화 | 4-bit NF4, compute dtype float16 |
| 디코딩 | **greedy** (`do_sample=False`) |
| max_new_tokens | 512 |

**샘플링을 끈 이유:** 약관 QA는 창의성이 아니라 정확한 전사가 필요하다. 온도를 주면 `2시간`이 `두 시간` 또는 `3시간`으로 바뀔 수 있다. 같은 질문에 같은 답을 내는 재현성도 채점 안정성에 유리하다.

T4에서 bge-m3(약 1.1GB)와 함께 올려야 하므로 3B 4-bit(약 2GB)로 시작했다. Pro+ A100이면 7B로 올릴 여지가 있으나, **채점 런타임이 T4**이므로 T4 기준으로 맞췄다.

### 5.2 프롬프트 설계: 근거 제한 (grounding)

시스템 프롬프트의 네 규칙:

1. **제공된 근거 조문에 있는 내용만 사용.** 근거 밖의 사실을 추가하지 않는다
2. **숫자·기간·조건·예외는 근거 문장 그대로 옮긴다.** 바꾸거나 반올림하지 않는다
3. 여러 약관에 같은 내용이 있으면 실제로 사용한 근거를 모두 남긴다 (P02 대비)
4. 지정된 JSON 형식만 출력한다

사용자 메시지에는 검색 상위 **4개 조문만** 넣는다. 규정이 "질문과 관계없이 약관 원문 전체를 매 질문의 프롬프트에 넣는 방식"을 금지하기도 하지만, 그보다 **무관한 조문이 생성 근거를 오염시키는 것**이 더 큰 문제다.

```
[S1] 카카오계정 약관 제10조(사업자/단체 카카오계정)
①사업자/단체 카카오계정은 …

[S2] …
```

### 5.3 구조화 출력과 근거 선택

모델은 `{"answer": "...", "used": ["S1", "S3"]}` 형태로 답한다. **모델이 실제로 사용한 근거만** `retrieved`에 남기기 위해서다 — 검색 후보 4개를 그대로 반환하면 계약("실제 답변에 사용한 근거를 1~4개")을 위반하고 정밀도가 떨어진다.

파싱 후 검증:

| 검사 | 처리 |
| --- | --- |
| `S번호`가 실제 후보 범위 밖 | 버림 |
| 중복 | 제거 |
| 4개 초과 | 앞 4개만 |
| JSON 파싱 실패 | 본문을 답변으로 쓰고 근거는 검색 1위로 폴백 |
| `used`가 빈 배열 | 검색 1위로 폴백 (계약상 최소 1개) |

4개 경로(정상 / 중복·범위밖 / JSON 아님 / 빈 값)를 모두 테스트해 **어떤 경우에도 `retrieved`가 1~4개의 유효한 `[문서명, 정수]`**임을 확인했다.

## 6. 런타임 구조

```
1번 셀 실행
 ├ 패키지 설치 (sentence-transformers, scikit-learn, accelerate, bitsandbytes)
 ├ 내장 스냅샷 해제 → SHA-256 + 조/항 수 검증          ← 실패 시 즉시 중단
 ├ TF-IDF 희소 인덱스 구축 (229 청크)
 ├ bge-m3 로드 → 229 청크 인코딩 → numpy 행렬 (0.94MB)
 ├ Qwen2.5-3B-Instruct 4-bit 로드
 └ FastAPI app (GET /health, POST /answer)

질문마다 (answer_question)
 └ 희소 순위 + 밀집 순위 → RRF → 조 max 집계 → 상위 4개
   → Qwen 생성 → JSON 파싱·검증 → {"answer", "retrieved"}
```

**모델·인덱스는 서버 기동 전 전역에서 한 번만 초기화한다.** 공통 러너가 동시 요청 2개를 보내지만 `_GENERATION_LOCK`이 GPU 생성을 직렬화하므로, 질문마다 재다운로드·재임베딩하지 않는다.

노트북 1번 셀 총 109KB, 그중 내장 스냅샷이 88KB다.

### 미검증 (1차 Colab 실행에서 확인할 것)

- Qwen2.5-3B 4-bit **로딩과 T4 VRAM 여유** (bge-m3와 동시 상주)

### 알려진 이슈

**정밀도.** 검색 전용 베이스라인은 항상 4개를 반환해 `precision@4 = 0.30`이었다(대부분 문항의 정답은 1개). 노트북에서는 Qwen이 `used`로 골라내므로 개선되지만, **채점식이 초과 근거를 감점하는지 확인되지 않았다.**

**공개셋 천장.** 공개 10문항은 희소 검색만으로도 포화 상태다. 이 점수로 개선을 판단할 수 없으며, 비공개 30문항이 실제 시험이다.
