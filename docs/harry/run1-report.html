1.2 파싱 — 문서별 규칙 분기

네 문서는 겉보기와 달리 “3+1” 구조다. 통합 약관(2022 아카이브)만 표기 체계가 완전히 다르다.

같은 N. 마커가 문서에 따라 항이거나 호다. 단일 규칙으로 통일하면 청크 계층이 무너진다. 계정 약관 제12조는 ①…아래 각 호의 행위는 뒤에 1. 2. …가 붙는 항–호 구조지만, 통합 약관 제10조는 1. 2. …가 곧 항이다.

ART  = r"^제\s*(\d+)\s*조\s*[\(（]?\s*([^)）]*?)\s*[\)）]?\s*$"
HEAD = {"circled": r"^[①-⑳]",     # 계정 / 위치정보 / 통합서비스
        "numdot":  r"^\d+\."}      # 통합 약관

조 헤더 정규식은 두 표기를 \s*로 흡수하고, 줄 전체 매칭이라 본문 중 상호참조(제14조 제1항에 따라…)는 자동 배제된다. 마커 없는 줄은 직전 항에 붙인다 — 통합 약관 제11조 4항(유료서비스 환불)은 4. 아래에 마커 없는 규정 줄이 이어지는데, 이를 떼면 “무슨 환불인지” 문맥을 잃는다.

본문만 임베딩하면 유사도 0.97짜리 두 조문의 벡터가 사실상 구분되지 않는다. 접두어가 붙으면 위치정보·Daum·통합서비스 같은 문서 고유 어휘가 벡터에 들어가 순위가 갈린다. 필터가 아니라 신호이므로 P02의 다중 정답도 살아남는다.

확정 근거는 지표가 아니다

지표 차이(hit@1 0.90 → 1.00)는 1문항이며, 공개 10문항은 희소 검색 단독으로도 hit@3 = 1.00인 천장 상태라 모델 우열의 근거가 되지 못한다. 반면 절단은 표본 크기와 무관한 결정론적 사실이다. 확정 근거는 절단 게이트 하나다.

8192 컨텍스트의 부수 이득: 2차 분할 로직 자체가 사라진다. 512토큰 모델을 쓰면 초과 청크를 문장 경계로 나누는 코드, 분할 청크의 부모 재매핑, 경계에서 잘린 문맥 처리가 전부 따라붙는다. 큰 모델을 고르는 것이 코드를 줄였다.

3.2 저장 — 벡터 DB를 쓰지 않는다

구분값
벡터 수 × 차원229 × 1024
밀집 행렬0.94 MB (float32)
질의당 연산23만 FLOP

L2 정규화한 numpy 행렬에 행렬곱 한 번이면 229개 전체에 대한 정확한 cosine 유사도가 나온다. FAISS·Chroma·Qdrant를 배제한 이유 셋:

  1. ANN이 해결하는 문제가 없다. HNSW/IVF는 전수 비교가 감당 안 되는 10만~100만 벡터에서 정확도를 조금 버리고 속도를 얻는 기법이다. 229개에서는 정확도만 버린다.
  2. 제출물이 노트북 1개다. 외부 DB 파일이나 영속 디렉터리를 둘 자리가 없다.
  3. 의존성이 실패 지점이다. faiss-cpu 설치 실패나 버전 불일치는 새 Colab 런타임에서 실제로 일어난다.

임베딩을 미리 계산해 노트북에 넣지도 않았다. 질의 인코딩에 어차피 모델이 필요하므로, 모델이 메모리에 있으면 229청크 인코딩은 몇 초짜리 초기화 비용에 불과하다.

희소 — TfidfVectorizer(analyzer="char_wb", ngram_range=(2,5), sublinear_tf=True). 문자 n-gram을 쓴 이유는 형태소 분석기(kiwi, mecab) 설치 없이 한국어 조사 변형을 흡수하기 위해서다. 보관합니다 / 보관하나요 / 보관이 모두 부분 매칭된다. 새 Colab에서 형태소 분석기 설치가 실패할 위험도 함께 제거된다.

4.2 Reciprocal Rank Fusion

두 검색기의 점수 스케일이 다르므로 점수를 직접 더할 수 없다 — TF-IDF cosine과 bge-m3 cosine은 분포가 다르다. RRF는 점수 대신 순위만 쓴다.

score(조) =  Σ    1 / (k + rank + 1)        k = 60, 상위 8개만 참여
          검색기별
  • k = 60 — 상위 순위 가중을 완만하게 하는 표준값. 1위와 2위의 격차를 과장하지 않는다.
  • depth = 8 — 각 검색기에서 상위 8개 조만 융합에 참여. 꼬리 잡음 차단.
  • 동점 처리 — RRF가 같으면 밀집 점수로 가른다(np.lexsort). 두 검색기 모두 상위에 못 올린 조는 융합 점수 0이므로 밀집 순으로 뒤에 붙는다.

4.3 부모 조 집계 — max, 평균 아님

평균을 쓰면 길이가 곧 페널티가 된다. 긴 조문일수록 질문과 무관한 항을 많이 갖기 때문이다. P09의 정답 카카오 통합 약관 제10조는 1,385자짜리 긴 조문이라 평균 집계에서 불리해진다.

scores = np.full(n_articles, -np.inf)
np.maximum.at(scores, parents, unit_scores)   # 항 → 부모 조 max

5 생성

5.1 모델

항목값
모델Qwen/Qwen2.5-3B-Instruct — 규정상 Qwen2.5-Instruct 계열 필수
양자화4-bit NF4 · compute dtype float16

샘플링을 끈 이유 — 약관 QA는 창의성이 아니라 정확한 전사가 필요하다. 온도를 주면 2시간이 두 시간 또는 3시간으로 바뀔 수 있다. 같은 질문에 같은 답을 내는 재현성도 채점 안정성에 유리하다.

T4에서 bge-m3(약 1.1GB)와 함께 올려야 하므로 3B 4-bit(약 2GB)로 시작했다. Pro+ A100이면 7B로 올릴 여지가 있으나, 채점 런타임이 T4이므로 T4 기준으로 맞췄다.

5.2 프롬프트 설계 — 근거 제한 (grounding)

  1. 제공된 근거 조문에 있는 내용만 사용. 근거 밖의 사실을 추가하지 않는다.
  2. 숫자·기간·조건·예외는 근거 문장 그대로 옮긴다. 바꾸거나 반올림하지 않는다.
  3. 여러 약관에 같은 내용이 있으면 실제로 사용한 근거를 모두 남긴다 P02 대비
  4. 지정된 JSON 형식만 출력한다.

사용자 메시지에는 검색 상위 4개 조문만 넣는다. 규정이 “질문과 관계없이 약관 원문 전체를 매 질문의 프롬프트에 넣는 방식”을 금지하기도 하지만, 그보다 무관한 조문이 생성 근거를 오염시키는 것이 더 큰 문제다.

①사업자/단체 카카오계정은 …

[S2] …

5.3 구조화 출력과 근거 선택

모델은 {"answer": "...", "used": ["S1", "S3"]} 형태로 답한다. 모델이 실제로 사용한 근거만 retrieved에 남기기 위해서다 — 검색 후보 4개를 그대로 반환하면 계약(“실제 답변에 사용한 근거를 1~4개”)을 위반하고 정밀도가 떨어진다.

파싱 후 검증 · 4개 경로 전부 테스트 완료
검사처리
S번호가 실제 후보 범위 밖버림
중복제거
4개 초과앞 4개만
JSON 파싱 실패본문을 답변으로 쓰고 근거는 검색 1위로 폴백
used가 빈 배열검색 1위로 폴백 — 계약상 최소 1개

어떤 경우에도 retrieved가 1~4개의 유효한 [문서명, 정수]임을 확인했다.

질문마다 — 희소 순위 + 밀집 순위 → RRF → 조 max 집계 → 상위 4개 → Qwen 생성 → JSON 파싱·검증 → {"answer", "retrieved"}

모델·인덱스는 서버 기동 전 전역에서 한 번만 초기화한다. 공통 러너가 동시 요청 2개를 보내지만 _GENERATION_LOCK이 GPU 생성을 직렬화하므로, 질문마다 재다운로드·재임베딩하지 않는다.

노트북 1번 셀 총 109KB, 그중 내장 스냅샷이 88KB다.
