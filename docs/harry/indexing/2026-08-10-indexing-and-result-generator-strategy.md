# 카카오 약관 인덱싱 및 결과기 전략

## 결론

제출물은 `src/result_generator.ipynb` 하나이므로, 원본 문서를 Colab 실행 중에
다운로드·파싱하지 않는다. 개발 환경에서 **목표 시행일의 공식 웹페이지 HTML/DOM을
주 입력으로 추출**하고, 동일 시행일의 DOCX가 있을 때 문단·번호를 교차 검증한다.
검증된 조문 JSON을 압축해 1번 셀에 내장한다.

질의 시에는 긴 조문의 항·호 단위 청크를 대상으로 한국어 문자 n-gram 희소 검색과
로컬 다국어 E5 밀집 검색을 결합한다. 점수는 부모 조문으로 집계하고, Qwen2.5-Instruct가
선택된 근거 문단만 사용해 답을 만든다. 반환하는 `retrieved`는 모델이 실제 사용한
부모 조문 1~4개로 제한한다.

이 방식은 다음을 동시에 만족한다.

- 새 Colab T4에서 개인 파일, Drive, 원격 검색 API 없이 재현된다.
- 네 약관 모두에서 목표 시행일과 조문 계층을 같은 방법으로 보존한다.
- 표현이 달라진 질문은 dense 검색으로, 숫자·법조문·고유명사는 희소 검색으로 보완한다.
- 72개 조문 규모에서는 벡터 DB나 근사 최근접 검색보다 정확한 전체 비교가 더 단순하고 빠르다.

## 1. 입력 형식 결정

### 최종 결정

이 프로젝트에서는 **공식 HTML/DOM → UTF-8 조문 JSON**을 주 경로로 사용한다.
동일한 목표 시행일의 DOCX가 실제로 제공되는 문서는 DOCX를 보조 검증 자료로 쓴다.
PDF는 육안 대조와 보존용, HWP는 최후의 대체 입력으로만 사용한다.

형식의 우선순위는 아래와 같다.

| 순위 | 형식 | 역할 | 근거 |
| ---: | --- | --- | --- |
| 1 | 공식 HTML/DOM | 주 추출 소스 | `h4`/`strong` 조 제목과 `ul`/`li` 항·호가 구조로 남고, 네 목표 버전에 모두 접근 가능하다. |
| 2 | 동일 시행일 DOCX | 문단·번호 교차 검증 | 문단과 OOXML 번호 정보가 보존되어 파일 형식 중 파싱 품질이 가장 좋다. |
| 3 | PDF | 보존·육안 대조 | 텍스트는 추출되지만 페이지 경계와 시각적 줄바꿈이 논리 문단을 훼손한다. |
| 4 | HWP | 다른 소스가 없을 때만 사용 | HWP 5.x 전용 파서·변환기가 필요하고 재현 가능한 Colab 파이프라인 구성이 가장 어렵다. |
| 제외 | 수동 복사 텍스트 | 긴급 복구용 | 구조와 출처 해시를 잃고 선택 누락·중복 같은 사람 오류를 검출하기 어렵다. |

여기서 말하는 "텍스트"는 브라우저에서 사람이 드래그해 복사한 평문이 아니다. 공식 페이지의
약관 컨테이너를 프로그램으로 읽어 DOM 요소의 종류와 순서를 유지한 구조화 텍스트다. HTML
원본 파일과 SHA-256을 함께 보관하므로 나중에도 추출 결과를 재현할 수 있다.

### 실제 파일 비교 근거

2026-05-29 카카오 통합서비스약관의 공식 DOCX·PDF·HWP를 직접 비교했다.

- DOCX는 빈 문단을 제외하고 135개 논리 문단을 제공했고, 그중 61개에 OOXML 번호 속성이
  있었다. 표 없이 본문 순서가 유지되며 조 제목도 독립 문단이다.
- 같은 내용의 PDF는 19페이지로 나뉜다. 텍스트 추출 시 하나의 항이 페이지 경계에서 끊기고
  `15일`이 `15 일`, `제3자`가 `제 3 자`처럼 바뀌어 추가 정규화가 필요했다.
- HWP는 `Hangul Word Processor 5.x` 바이너리다. 텍스트가 이미지인 것은 아니지만 DOCX처럼
  표준 ZIP/XML 도구로 읽을 수 없어 별도 파서 실패 가능성이 생긴다.
- DOCX가 파일 형식만 놓고 보면 가장 좋지만, 공식 다운로드 구성은 목표 버전마다 균일하지
  않다. 카카오계정 약관 다운로드는 현재 페이지의 2026-05-29 본문과 달리 2024-04-16 파일을
  가리키고, 위치정보 이용약관 페이지에는 같은 다운로드 묶음이 없다. 아카이브 페이지의
  다운로드 레이어도 2022-08-25 카카오 통합 약관 파일을 보장하지 않는다.

따라서 DOCX 하나로 네 문서를 통일하면 **잘 파싱된 잘못된 버전**을 만들 위험이 있다. 정확한
시행일을 우선하고, 구조가 분명한 공식 HTML/DOM을 공통 입력으로 선택한다.

PDF도 RAG 인덱싱은 가능하다. 다만 PDF 바이너리를 직접 검색하지 않고 텍스트를 추출한 다음
`제N조 (제목)`과 항·호를 복원해 조문 JSON으로 바꿔야 한다. 목표 버전 HTML을 얻지 못하는
경우에만 PDF 추출을 대체 경로로 사용한다.

대상 원문과 확인값은 아래처럼 고정한다.

| 문서명 | 시행일 | 예상 조문 수 | 원문 |
| --- | --- | ---: | --- |
| 카카오계정 약관 | 2026-05-29 | 17 | [공식 페이지](https://www.kakao.com/policy/terms?type=a&lang=ko) |
| 카카오 위치정보 이용약관 | 2026-07-16 | 16 | [공식 페이지](https://www.kakao.com/policy/location?lang=ko) |
| 카카오 통합서비스약관 | 2026-05-29 | 18 | [공식 페이지](https://www.kakao.com/policy/terms?type=ts&lang=ko) |
| 카카오 통합 약관 | 2022-08-25 | 21 | [공식 아카이브](https://www.kakao.com/policy/kakaoTerms) |

아카이브 문서는 종료 안내일이 아니라 **시행일 2022-08-25**를 버전 메타데이터로 사용한다.
검색 결과의 문서명은 평가 계약에 맞춰 `카카오 통합 약관`으로만 반환한다.

## 2. 데이터 준비: 개발 단계에서 한 번만 수행

이 단계의 HTML, 검증용 DOCX/PDF와 중간 JSON은 개발용이다. 최종 제출 노트북은 어느 외부
파일도 읽지 않는다.

### 2.1 원본 수집과 보존

1. 네 공식 URL의 HTML을 내려받고 문서 식별자·시행일을 파일명에 넣어 고정한다.
2. URL, HTML SHA-256, 다운로드 시각, 시행일을 `source_manifest.json`에 기록한다.
3. 약관 본문 컨테이너 안에서 조 제목과 다음 조 제목 사이의 문단·목록만 순서대로 읽는다.
   사이트 메뉴, 다운로드 레이어, 공통 푸터, 변경 전 약관 링크는 제외한다.
4. `h4` 또는 `strong.tit_subject`를 조 제목으로, `p`를 문단으로, `li`를 항·호·목록으로
   매핑한다. 유니코드는 NFC로 통일하고 연속 공백만 정규화한다.
5. 동일 시행일 DOCX가 있으면 `python-docx`로 문단과 번호 속성을 추출해 조 제목·본문을
   교차 검증한다. PDF는 시행일과 대표 문장을 육안 대조하는 보존 자료로 쓴다.
6. HTML을 얻지 못한 문서만 DOCX → PDF → HWP 순서의 대체 경로로 처리한다. 수동 복사 텍스트는
   마지막 복구 수단이며, 사용할 경우 두 사람이 원문 전체를 대조한다.

### 2.2 조문 JSON으로 정규화

최소 스키마는 다음과 같다. `search_text`에는 문서명·시행일·조 제목·본문을 모두 넣고,
`body`에는 원문 순서를 보존한다.

```json
{
  "schema_version": 1,
  "documents": [
    {
      "doc_id": "account_20260529",
      "name": "카카오계정 약관",
      "effective_date": "2026-05-29",
      "source_url": "https://www.kakao.com/policy/terms?type=a&lang=ko",
      "source_sha256": "...",
      "articles": [
        {
          "article": 7,
          "title": "카카오계정 제공",
          "body": "...",
          "units": [
            {"unit_id": "7-1", "label": "①", "text": "..."},
            {"unit_id": "7-2", "label": "②", "text": "..."}
          ]
        }
      ]
    }
  ]
}
```

`units`는 가능한 한 원래 항·호·목록을 한 단위로 보존한다. 한 항이 매우 길 때만 문장 경계를
우선해 350~800자 보조 청크로 나눈다. 어떤 보조 청크도 조 번호를 잃지 않으며, 나뉜 청크의
부모는 항상 하나의 `(문서명, 조 번호)`다.

### 2.3 수집 검증 게이트

인덱스를 만들기 전에 아래가 모두 참인지 자동 검사한다.

- 네 문서명과 시행일이 위 표와 정확히 일치한다.
- 조문 수가 각각 17, 16, 18, 21이며, 각 문서의 조 번호가 연속된다.
- 모든 조문에 제목·본문이 있고 본문이 비어 있지 않다.
- 조문 제목과 시행일이 고정 HTML에서 일치하고, 동일 시행일 DOCX/PDF가 있으면 대표 조문도
  교차 검증한다.
- 전체 정규화 JSON의 SHA-256을 만든다.
- 공개 골드셋의 모든 `(doc, article)` 조합이 스냅샷에 존재한다. 이 검사는 답을 외우기 위한
  규칙이 아니라 데이터 누락 검출용이다.

## 3. 제출 노트북에 데이터를 넣는 방법

노트북만 제출하므로 `data/terms.json`, `src/rag.py`, Git 저장소 경로, Drive를 읽는 구현은
제출 환경에서 실패한다. 현재 비어 있는 `src/rag.py`는 로컬 실험용으로만 사용하고, 제출 전에는
필요한 코드와 데이터가 모두 1번 셀 안에 있어야 한다.

개발 단계에서 정규화 JSON을 UTF-8로 직렬화하고 `gzip + base64`로 압축한다. 그 결과 문자열과
원본 JSON의 SHA-256을 1번 셀 상단 상수에 넣는다.

```python
TERMS_SNAPSHOT_B64 = "H4sI..."  # 개발 단계에서 생성한 고정 문자열
TERMS_SNAPSHOT_SHA256 = "..."

def load_terms_snapshot():
    raw = gzip.decompress(base64.b64decode(TERMS_SNAPSHOT_B64))
    if hashlib.sha256(raw).hexdigest() != TERMS_SNAPSHOT_SHA256:
        raise RuntimeError("내장 약관 스냅샷 무결성 검증 실패")
    snapshot = json.loads(raw.decode("utf-8"))
    validate_snapshot(snapshot)
    return snapshot
```

이 크기의 약관(총 약 4.9만 자, 72개 조문)은 압축 후에도 노트북에 무리 없이 포함된다. 원본
HTML/DOCX/PDF를 base64로 넣고 Colab에서 다시 파싱하는 방법은 노트북이 커지고 초기화·파싱
오류를 늘리므로 선택하지 않는다.

## 4. 1번 셀의 기본 구현 순서

먼저 단순하지만 완결된 수직 슬라이스를 만들고, 그 뒤 검색 성능을 개선한다. 처음부터 대형
리랭커를 붙이면 어느 단계에서 품질이 좋아지거나 나빠졌는지 판단하기 어렵다.

### 단계 A: 데이터 로드와 희소 검색 기준선

1. 1번 셀의 팀 자유 구현 영역에 패키지 설치, 내장 스냅샷 해제, 스키마 검증 코드를 넣는다.
   기존 FastAPI 영역과 2번 공통 러너는 변경하지 않는다.
2. 각 `unit`에 부모 메타데이터(`doc_name`, `article`, `article_title`, `effective_date`)를 붙인다.
3. `TfidfVectorizer(analyzer="char_wb", ngram_range=(2, 5), sublinear_tf=True)`로 희소 인덱스를 만든다.
   한국어 조사는 형태소 분석기 없이도 문자 n-gram이 안정적으로 처리한다.
4. 질문과 전체 청크의 cosine score를 정확 계산하고, 같은 부모 조문 청크의 최대 점수를 조문 점수로
   집계한다. 상위 6개 조문 후보와 해당 최고 점수 청크를 남긴다.
5. 후보 2~4개를 짧은 근거 문단으로 구성해 Qwen에 전달하고, `answer_question()`이
   `{"answer": str, "retrieved": [[문서명, 조번호], ...]}`를 반환하게 만든다.

이 시점에 이미 공통 러너를 통과하는 결과기가 된다. 이후 개선은 이 기준선의 회귀 테스트를
통과할 때만 반영한다.

### 단계 B: Qwen 답변 생성과 근거 반환을 견고하게 만들기

- 기본 후보 모델은 `Qwen/Qwen2.5-3B-Instruct`의 4-bit 로컬 로딩으로 시작한다. T4에서 시작
  시간과 36회 성능 측정의 지연시간을 확인한 뒤, 품질 이득이 충분할 때만 7B 4-bit를 비교한다.
- `temperature=0`, 작은 `max_new_tokens`(예: 220)로 수치·조건을 변형하지 않게 한다.
- 프롬프트에는 `[S1] 문서명 제N조`처럼 후보 ID와 원문 근거만 넣고, "제공된 근거 밖의 사실을
  추가하지 말 것"을 명시한다.
- 모델 출력은 `answer`와 `used_source_ids`를 포함한 JSON으로 요구한다. 파싱 후 ID가 실제 후보인지,
  1~4개인지, 부모 조문이 중복되지 않는지 검증한다.
- JSON 파싱에 실패하면 답변 텍스트를 안전하게 정리하고 검색 상위 조문으로 fallback한다. 빈
  `retrieved`나 허용되지 않은 문서명은 반환하지 않는다.

공통 러너는 HTTP 요청을 동시에 두 개 보내지만, 제공된 `_GENERATION_LOCK`이 GPU 생성을 직렬화한다.
따라서 모델·인덱스는 서버 기동 전에 전역으로 한 번만 초기화하고, 매 질문마다 재다운로드·재임베딩·
재로딩하지 않는다.

### 단계 C: 하이브리드 검색으로 성능 개선

희소 기준선의 점수와 공개 골드셋을 기록한 뒤에만 추가한다.

1. `intfloat/multilingual-e5-small`을 Colab에 로컬로 내려받아 실행한다. 외부 임베딩 API가 아니라
   로컬 모델 추론이어야 한다.
2. 청크 임베딩은 초기화 때 한 번 만들고 L2 정규화한다. 질문에는 `query:`, 문서에는 `passage:`
   접두어를 사용한다.
3. 청크 수가 매우 작으므로 FAISS 없이 `query_vector @ passage_matrix.T`로 모든 cosine score를
   정확 계산한다.
4. 희소 상위 8개와 dense 상위 8개를 Reciprocal Rank Fusion(RRF)으로 결합한다.
5. 문서명을 직접 언급한 질문에는 약한 문서 가산점만 준다. 문서명을 언급하지 않는 공통 질문과
   여러 문서가 근거인 질문을 위해 문서 필터링은 하지 않는다.
6. 청크 점수를 부모 조문으로 집계하고, 동일 조문은 하나만 남긴다. 상위 후보에서 유사 조항이
   서로 다른 약관에 함께 강하게 나타나면 문서 다양성을 보존한다. 이는 P02 같은 다중 근거 질문의
   회수율을 높인다.

별도 cross-encoder 리랭커는 첫 구현에 넣지 않는다. 72개 조문에서는 하이브리드 후보와 Qwen의
근거 선택만으로 먼저 측정하고, 정확 조문 회수율이 병목일 때만 작은 로컬 리랭커를 비교한다.

## 5. 추천 코드 경계

제출 시에는 모두 1번 셀 안에 놓되, 개발 중에는 아래 책임으로 나누어 테스트한다.

| 개발용 단위 | 책임 | 제출 시 위치 |
| --- | --- | --- |
| `build_terms_snapshot` | HTML DOM 추출, DOCX/PDF 대조, 조문 JSON·압축 문자열 생성 | 개발 스크립트 전용 |
| `validate_snapshot` | 문서명·시행일·조문 수·해시 검사 | 1번 셀 |
| `build_chunks` | 항·호 보존 청크와 부모 매핑 생성 | 1번 셀 |
| `HybridRetriever` | sparse/dense 점수, RRF, 부모 조문 집계 | 1번 셀 |
| `AnswerGenerator` | Qwen 로딩, 제한된 근거 프롬프트, 구조화 출력 파싱 | 1번 셀 |
| `answer_question` | 검색 → 근거 선택 → 답변 → 반환 계약 보장 | 1번 셀 |

`src/result_generator.ipynb`의 고정 FastAPI 연결 영역은 그대로 둔다. `answer_question` 위의 자유
구현 영역에서 전역 결과기 객체를 한 번 만들고, 함수는 그 객체를 호출만 하도록 한다.

## 6. 평가와 최적화 순서

공개 10문항은 비공개 문제를 대표하지 않으므로, 특정 문항의 단어·조문 번호를 하드코딩하지 않는다.
대신 아래 지표로 일반적인 검색 결정을 비교한다.

| 지표 | 계산 | 목적 |
| --- | --- | --- |
| Exact article Recall@1/@3/@5 | `(문서명, 조 번호)` gold가 상위 k에 있는 비율 | 근거 조문 회수 확인 |
| All-gold coverage@k | 다중 gold 문항에서 회수한 gold 수 / 전체 gold 수 | P02 같은 병렬 근거 확인 |
| MRR | 첫 gold 조문의 역순위 평균 | 최상위 근거 품질 확인 |
| Key-fact 충족률 | `key_facts`별 답변 포함·왜곡 여부 수동 점검 | 생성 답변 품질 확인 |
| p50/p95 지연시간·성공률 | 2번 공통 러너의 성능 블록 | 120초 제한과 안정성 확인 |

실험은 다음 순서를 지킨다.

1. sparse-only + Qwen 기준선을 실행하고 검색 순위와 답을 저장한다.
2. dense-only를 비교한다.
3. sparse+dense RRF를 비교한다.
4. 부모 조문 집계, 문서 가산점, 문서 다양성 규칙을 하나씩 추가·제거해 효과를 기록한다.
5. 3B와 7B의 답변 품질·p95 지연시간을 같은 설정에서 비교한다.
6. 선택한 조합, 스냅샷 해시, 패키지·모델 버전을 문서에 고정하고 새 Colab에서 재실행한다.

## 7. 완료 조건

- 새 Colab T4에서 노트북의 두 셀만 위에서 아래로 실행된다.
- 셀 내부의 내장 스냅샷만으로 네 약관 72개 조문을 복원하고 무결성 검사를 통과한다.
- `answer_question`은 모든 정상 질문에서 허용 문서명과 정수 조 번호의 근거 1~4개를 반환한다.
- 공개 러너의 10문항, 워밍업 2회, 성능 측정 12요청 × 3회가 오류·시간초과 없이 끝난다.
- 최종 선택안의 검색·답변·지연시간 결과와 snapshot SHA-256이 기록되어 다시 비교할 수 있다.

## 처음 바로 할 일

1. 네 공식 HTML을 고정하고, 제공되는 동일 시행일 DOCX/PDF로 검증해 `terms_snapshot.json`을 만든다.
2. JSON을 압축 내장한 sparse-only 결과기를 1번 셀의 자유 구현 영역에 만든다.
3. 2번 공통 러너로 계약과 공개 10문항을 먼저 통과시킨다.
4. 그 뒤 dense E5와 RRF를 추가해 검색 성능을 비교한다.

이 순서는 데이터 누락, 반환 형식, 모델 생성, 검색 품질을 한 번에 디버깅하지 않도록 하며,
가장 빠르게 제출 가능한 기준선을 만든다.
