| 항목 | 선택 | 근거 |
| --- | --- | --- |
| 파싱 | 정규식 규칙 기반, **문서별 항 마커 정책 분리** | `1.`이 세 문서에서는 호, 통합 약관에서는 항. 단일 규칙으로 통일 불가 |

| 희소 검색 | `TfidfVectorizer(analyzer="char_wb", ngram_range=(2,5))` | 숫자·법령 인용(`제16조 제2항`, `6개월`, `2시간`)은 dense가 자주 놓침 |

## 1. 데이터 실측

`analyze.py` 실측값. 4개 파일 전부 UTF-8, NFC 정규화 상태, NBSP 없음.

| 문서명 | 파일 | 조 | 장 | 본문 자수 | 조 길이 p50 / max |
| --- | --- | ---: | --- | ---: | --- |
| 카카오계정 약관 | `카카오계정_약관.txt` | 17 | 5 | 11,055 | 632 / 1,680 |
| 카카오 위치정보 이용약관 | `카카오_위치정보_이용약관.txt` | 16 | 없음 | 5,739 | 391 / 682 |
| 카카오 통합서비스약관 | `카카오_통합서비스약관` ※확장자 없음 | 18 | 4 | 14,957 | 643 / 3,482 |
| 카카오 통합 약관 | `카카오_통합_약관.txt` | 21 | 4 | 17,860 | 654 / 2,488 |

**총 72개 조문 / 47,938자.** 네 문서 모두 조 번호가 1부터 빈틈 없이 연속한다. 공개 골드셋 12개 `(문서, 조)` 쌍이 파싱 결과에 전부 존재한다.

### 코퍼스가 작다는 사실이 설계를 지배한다

47,938자는 A4 25쪽 수준이다. 이 규모에서는 **인덱싱 비용이 전부 무시 가능**하다. 따라서 "빠른 근사" 대신 "느려도 정확"을 일관되게 선택한다. 벡터 DB를 쓰지 않는 이유, 더 큰 임베딩 모델을 쓰는 이유가 모두 여기서 나온다.

### 최대 리스크: 문서 간 중복 조항

문자 3-gram Jaccard > 0.4인 **문서 간 조문 쌍이 30건**이다.

| 유사도 | 조문 A | 조문 B |
| ---: | --- | --- |
| 0.97 | 카카오계정 약관 제14조(회원에 대한 통지 및 공지) | 카카오 통합서비스약관 제17조(통지 및 공지) |
| 0.91 | 카카오계정 약관 제13조(개인정보의 보호) | 카카오 통합 약관 제15조(개인정보의 보호) |
| 0.89 | 카카오계정 약관 제17조(분쟁의 해결) | 카카오 통합서비스약관 제18조(분쟁의 해결) |
| 0.80 | 카카오계정 약관 제8조(카카오계정 서비스의 변경 및 종료) | 카카오 통합서비스약관 제7조(통합서비스의 변경 및 종료) |

공개 골드셋이 이 구조를 정면으로 겨냥한다.

- **P02**: 같은 사실("2시간 이상 지연 시 공지")이 3개 문서에 있고 **셋 다 정답**이다 → 문서 다양성을 유지해야 한다.
- **P08**(trap): `제3조 약관 외 준칙`은 네 문서 모두에 있는데 **카카오 통합 약관 제3조만 정답**이다 → 문서를 특정해야 한다.

즉 문서 판별을 못 하면 회수는 되는데 오답이 섞인다. 인덱싱 단계에서 대응할 부분은 **모든 임베딩 청크에 문서명과 조 제목을 본문 앞에 붙이는 것**이다(§3.3).

## 2. 파싱 설계

### 2.1 입력 고정

```python
FILES = {
    "카카오계정 약관":        ("카카오계정_약관.txt",      "2026-05-29"),
    "카카오 위치정보 이용약관":  ("카카오_위치정보_이용약관.txt", "2026-07-16"),
    "카카오 통합서비스약관":     ("카카오_통합서비스약관",      "2026-05-29"),  # 확장자 없음
    "카카오 통합 약관":        ("카카오_통합_약관.txt",      "2022-08-25"),
}
```

딕셔너리 키는 제출 포맷의 문서명과 **글자 단위로 일치**해야 한다(`answers_public_example.json` 계약). glob으로 파일을 훑지 않고 명시적으로 매핑한다 — 확장자 없는 파일 하나 때문에 glob 패턴이 조용히 3개만 잡는 사고를 막는다.

### 2.2 조·장 경계

```python
ART  = re.compile(r'^제\s*(\d+)\s*조\s*[\(（]?\s*([^)）]*?)\s*[\)）]?\s*$')
CHAP = re.compile(r'^제\s*(\d+)\s*장\s*(.*)$')
```

문서마다 표기가 다르므로 `\s*`로 흡수한다.

| 표기 | 문서 |
| --- | --- |
| `제 1 조 (목적)` — 공백 있음, 괄호 있음 | 계정, 위치정보, 통합서비스 |
| `제1조 목적` — 공백 없음, 괄호 없음 | 통합 약관 |

`CHAP`은 `ART`가 먼저 매치되지 않은 줄에만 적용한다. 위치정보 약관에는 장이 없으므로 장을 필수 필드로 두지 않는다.

### 2.3 항 마커 — 문서별로 다르다

가장 중요한 파싱 결정. **같은 `N.` 마커가 문서에 따라 항이거나 호다.**

| 문서 | 항 마커 | 호 마커 | 실측 |
| --- | --- | --- | --- |
| 카카오계정 약관 | `①`~`⑳` | `N.` | ① 42회, `N.` 56회 |
| 카카오 위치정보 이용약관 | `①`~`⑳` | `N.` | ① 36회, `N.` 18회 |
| 카카오 통합서비스약관 | `①`~`⑳` | `N.` | ① 57회, `N.` 44회 |
| **카카오 통합 약관** | **`N.`** | 마커 없음 | 원문자 0회, `N.` 70회 |

근거 — 계정 약관 제12조는 `①…아래 각 호의 행위는` 뒤에 `1.` `2.` … 가 붙는 전형적 항-호 구조다. 반면 통합 약관 제10조는 `1.` `2.` … 가 곧 항이고 그 아래 마커가 없다.

```python
HEAD = {"circled": re.compile(r'^([①-⑳])\s*'),   # 계정 / 위치정보 / 통합서비스
        "numdot":  re.compile(r'^(\d+)\.\s*')}    # 통합 약관
```

**마커 없는 줄은 직전 유닛에 붙인다.** 통합 약관 제11조 4항(유료서비스 환불 규정)은 `4.` 아래에 마커 없는 규정 줄이 여러 개 이어진다. 이 줄들을 독립 청크로 떼면 "무슨 환불인지" 문맥을 잃는다. 조 첫 줄이 마커 없이 시작하는 경우(위치정보 제8조 등 단문 조항)도 같은 규칙으로 자연히 처리된다.

### 2.4 정규화

검색 재현율에만 영향을 주고 원문 의미는 건드리지 않는 범위로 제한한다.

- 유니코드 NFC (이미 4개 파일 모두 만족 — 방어적으로만 수행)
- 곡선 따옴표 `‘’“”` → `'` `"` (문서당 6~22회)
- 중점 `・`(U+30FB) → `·`(U+00B7) — 위치정보 약관에 15회. `수집·이용·제공` 질의 매칭에 직접 영향
- 연속 공백/탭 → 공백 1개, 줄 양끝 trim, 빈 줄 제거

**하지 않는 것**: 숫자 표기 변경, 조사 분리, 괄호 제거, 띄어쓰기 교정. `제16조 제2항`, `6개월`, `2시간` 같은 토큰이 그대로 남아야 희소 검색이 P02·P05를 잡는다.

조 제목의 공백 편차(`제 1 조` vs `제1조`)는 파싱 시 흡수하고, 출력 인용 문자열은 `f"{문서명} 제{n}조({제목})"` 한 가지 형태로만 생성한다.

### 2.5 파싱 검증 게이트 — 통과 못 하면 인덱싱 중단

| 검사 | 기대값 |
| --- | --- |
| 조문 수 | 17 / 16 / 18 / 21, 합계 72 |
| 조 번호 연속성 | 각 문서 `1..N` 빈틈 없음 |
| 제목 | 72개 조문 전부 비어 있지 않음 |
| 본문 | 72개 조문 전부 비어 있지 않음, 최소 85자 이상 |
| 골드 커버리지 | 공개 골드셋 12개 `(문서, 조)` 쌍이 전부 존재 |
| 시행일 | 파일 끝의 `시행일자` 줄이 §2.1 상수와 일치 |
| 문서명 | 4개 키가 `answers_public_example.json`의 문서명과 정확히 일치 |
| 원문 해시 | 파싱 입력 4개 파일의 SHA-256 기록 |

마지막 항목이 필요한 이유: 현재 `data/카카오_통합_약관.txt`에 커밋되지 않은 수정이 남아 있다. 인덱스를 만든 시점의 원문을 해시로 고정하지 않으면 나중에 결과를 재현할 수 없다.

## 3. 청킹 설계

### 3.1 두 층 구조 (small-to-big)

```
조(article)  ← 검색 점수 집계 단위, 인용 단위, LLM에 넘기는 근거 단위
  └ 항(unit) ← 임베딩·희소 인덱싱 단위
```

조를 그대로 임베딩할 수 없다. 조 길이 p90이 1,529자, 최대 3,482자다. 다국어 sentencepiece 기준 한국어는 대략 1토큰당 1.1~1.3자이므로 최대 조문은 약 2,800~3,100토큰이고, 512토큰 모델에서는 뒷부분이 잘린다.

반대로 항을 그대로 인용할 수도 없다. 제출 포맷의 `retrieved`가 `[문서명, 조번호]`뿐이라 항 번호를 담을 자리가 없다.

### 3.2 항 청크 실측

| 지표 | 값 |
| --- | ---: |
| 총 청크 수 | **229** |
| 길이 p50 / p75 / p90 / p95 / max | 159 / 274 / 367 / 527 / 1,812자 |
| 500자 초과 | 15개 (7%) |
| 900자 초과 | 2개 (1%) |

문서별 청크 수는 계정 47 / 위치정보 43 / 통합서비스 63 / 통합 76이다.

900자를 넘는 두 청크는 `카카오 통합서비스약관 제12조 1항`(1,812자)과 `카카오계정 약관 제12조 1항`(1,218자)으로, 둘 다 "아래 각 호의 행위를 하여서는 안 된다" + 금지행위 열거 구조다. **호를 쪼개지 않는다** — 열거 항목 하나만 검색되면 무슨 목록인지 알 수 없다.

### 3.3 임베딩 텍스트 조립

각 청크를 임베딩할 때 본문 앞에 문서명과 조 제목을 붙인다.

```python
chunk_text = f"{doc_name} 제{article}조({article_title})\n{unit_text}"
```

§1의 중복 조항 30쌍에 대한 직접적인 대응이다. 본문만 임베딩하면 `카카오계정 약관 제14조`와 `카카오 통합서비스약관 제17조`(유사도 0.97)의 벡터가 사실상 구분되지 않는다. 접두어가 붙으면 "위치정보", "Daum", "통합서비스" 같은 문서 고유 어휘가 벡터에 들어가 P08 같은 문서 특정 질문의 순위가 갈린다.

E5 계열을 쓸 경우 여기에 추가로 `query:` / `passage:` 접두어가 필요하다. bge-m3는 접두어를 쓰지 않는다.

### 3.4 부모 집계

같은 조에 속한 항 청크들의 점수 중 **최댓값**을 그 조의 점수로 삼는다.

평균이 아니라 최댓값인 이유: 긴 조문일수록 질문과 무관한 항을 많이 갖는데, 평균을 쓰면 길이가 곧 페널티가 된다. P09의 정답인 `카카오 통합 약관 제10조`는 1,385자짜리 긴 조문이라 평균 집계에서 불리해진다.

## 4. 임베딩 모델 선택

| 후보 | 파라미터 | 차원 | 컨텍스트 | 판단 |
| --- | ---: | ---: | ---: | --- |
| **`BAAI/bge-m3`** | 568M | 1024 | 8192 | **1순위.** 229개 청크 전부 무손실. 한국어 검색 성능 우수 |
| `intfloat/multilingual-e5-base` | 278M | 768 | 512 | 2순위·기준선. 500자 초과 15개 청크 2차 분할 필요 |
| `intfloat/multilingual-e5-small` | 118M | 384 | 512 | 최소 기준선. 속도 이점이 이 규모에선 무의미 |
| `jhgan/ko-sroberta-multitask` | 111M | 768 | 512 | 한국어 전용이나 STS 학습이라 비대칭 검색에 약함 |

### bge-m3를 1순위로 두는 이유

1. **8,192 컨텍스트 → 2차 분할 로직 자체가 사라진다.** 512토큰 모델을 쓰면 500자 초과 15개 청크를 문장 경계로 나누는 코드, 분할 청크의 부모 매핑, 경계에서 잘린 문맥 처리가 전부 따라붙는다. 큰 모델을 고르는 것이 코드를 줄인다.
2. **인코딩 비용이 무의미하다.** 229개 청크를 딱 한 번 인코딩한다. T4에서 수 초다. 질의당 비용은 질문 1건 인코딩(수십 ms)뿐이다. 여기서 작은 모델을 골라 아끼는 것이 없다.
3. **VRAM이 남는다.** T4 16GB에서 Qwen2.5-7B-Instruct 4-bit가 약 5GB, bge-m3 fp16이 약 1.1GB다.

한국어 파인튜닝 변형(`nlpai-lab/KURE-v1`, `dragonkue/bge-m3-ko` 등)은 bge-m3 기준선을 세운 **뒤에** 같은 조건에서 Recall@3로 비교한다. 벤치마크 점수를 근거로 미리 채택하지 않는다.

### 결정 방법

공개 10문항 12개 골드쌍에 대해 dense-only Recall@1/@3/@5를 재고, **차이가 1문항(8%p) 이하면 더 단순한 쪽(e5-base)을 택한다.** 10문항 표본에서 1문항 차이는 잡음이다.

## 5. 데이터베이스 선택

### 결론: 벡터 DB를 쓰지 않는다

| 구분 | 값 |
| --- | --- |
| 벡터 수 | 229 |
| 차원 | 1024 (bge-m3) |
| 밀집 행렬 크기 | 229 × 1024 × 4B = **0.94MB** |
| 질의당 연산 | `(1,1024) @ (1024,229)` = 23만 FLOP |

L2 정규화한 numpy 행렬 하나에 행렬곱 한 번이면 **229개 전체에 대한 정확한 cosine 유사도**가 나온다. T4에서 1ms 미만, CPU에서도 5ms 미만이다.

FAISS·Chroma·Qdrant를 쓰지 않는 이유:

1. **ANN이 해결하는 문제가 여기 없다.** HNSW/IVF는 전수 비교가 감당 안 되는 10만~100만 벡터 이상에서 정확도를 조금 버리고 속도를 얻는 기법이다. 229개에서는 정확도만 버린다.
2. **제출물이 노트북 1개다.** 외부 DB 파일이나 영속 디렉터리를 둘 자리가 없다. FAISS 인덱스를 base64로 노트북에 넣는 것은 numpy 배열보다 나은 점이 없다.
3. **의존성이 실패 지점이다.** `faiss-cpu` 설치 실패나 버전 불일치는 새 Colab 런타임에서 실제로 일어난다.

임베딩을 미리 계산해 노트북에 박아 넣는 것도 하지 않는다. 질의 인코딩에 어차피 모델이 필요하므로 모델을 로드해야 하고, 그러면 229개 인코딩은 몇 초짜리 초기화 비용에 불과하다.

### 희소 인덱스도 같은 판단

`sklearn.feature_extraction.text.TfidfVectorizer(analyzer="char_wb", ngram_range=(2,5), sublinear_tf=True)` 하나면 된다. 문자 n-gram을 쓰는 이유는 형태소 분석기(kiwi, mecab) 설치 없이 한국어 조사 변형을 흡수하기 위해서다. `보관합니다` / `보관하나요` / `보관` 이 모두 부분 매칭된다.

희소가 반드시 필요한 근거는 실측된 질의 유형이다.

| 질문 | 결정적 토큰 | dense 단독 위험 |
| --- | --- | --- |
| P02 | `2시간` | 숫자가 벡터에서 희석됨 |
| P05 | `제16조 제2항`, `6개월` | 법령 인용은 위치정보 약관에만 4건 |
| P07 | `카카오 T택시`, 괄호 영문 | 고유명사, 통합 약관에 영문 54건 |

## 6. 인덱스 스키마

```python
{
  "articles": [                       # 72개 — 검색·인용 단위
    {"doc": "카카오계정 약관", "article": 7, "title": "카카오계정 제공",
     "chapter": 3, "effective_date": "2026-05-29",
     "text": "…조문 전문(항 순서 보존)…",
     "citation": "카카오계정 약관 제7조(카카오계정 제공)"}
  ],
  "units": [                          # 229개 — 임베딩·희소 인덱싱 단위
    {"parent": 6,                     # articles 배열의 인덱스
     "label": "①", "order": 1,
     "text": "…항 원문…",
     "embed_text": "카카오계정 약관 제7조(카카오계정 제공)\n…항 원문…"}
  ],
  "source_sha256": {"카카오계정 약관": "…", …}
}
```

`units[].parent`를 배열 인덱스로 두면 집계가 `np.maximum.at(article_scores, parents, unit_scores)` 한 줄이 된다. `(문서명, 조번호)` 튜플을 키로 딕셔너리를 도는 것보다 단순하다.
