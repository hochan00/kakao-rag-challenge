# 인덱싱 규정 경계와 적대적 검증 기준

작성일 2026-08-10. 목적은 운영진 공지에서 명시된 사실, 명시되지 않아 팀이 선택한 사항, 그 선택의 검증 방법을 분리하는 것이다. 이 문서는 구현 전략이 아니라 검증용 기록이다. 구체적인 파싱·청킹·검색 설계는 [인덱싱 설계](2026-08-10-indexing-design.md), 원문 실측은 [약관 데이터 특성](2026-08-10-terms-data-characteristics.md)을 기준으로 한다.

## 1. 판정 요약

**임베딩 모델과 데이터베이스는 운영진이 고정하지 않았다.**

고정된 모델 제약은 생성형 LLM의 Qwen2.5-Instruct 계열뿐이다. 원격 임베딩·리랭커와 원격 관리형 검색 서비스는 금지된다. 따라서 Colab T4 런타임 안에서 실행되는 로컬 임베딩 모델과 로컬 인덱스는 규정과 양립하지만, 특정 모델·DB가 운영진에 의해 허용 목록으로 확인된 것은 아니다. 이 차이를 문서와 발표에서 혼동하지 않는다.

## 2. 규정 사실과 팀 판단의 분리

| 항목 | 판정 | 근거 또는 한계 |
| --- | --- | --- |
| 생성 모델 | **고정** | Qwen2.5-Instruct 계열만 사용한다. |
| 생성 모델의 크기·양자화·미세조정·추론 설정 | **자유** | 결과기 규정의 자유 선택 항목이다. |
| 임베딩 모델명·차원·양자화 | **명시 없음** | E5·BGE 등 어떤 특정 모델도 공지에 없다. |
| 로컬 임베딩·로컬 리랭커 | **규정상 가능하다고 해석** | 원격 임베딩·리랭커만 금지됐다. 새 Colab 안에서 로컬로 추론해야 한다. |
| 원격 임베딩·리랭커 API | **금지** | 외부 서비스 호출로 벡터·재순위를 얻을 수 없다. |
| 원격 관리형 검색·벡터 DB | **금지** | 외부 Pinecone·관리형 OpenSearch 등은 사용하지 않는다. |
| 로컬 DB·인메모리 인덱스 | **명시적 지정 없음, 규정상 가능하다고 해석** | DB 제품은 공지에 없다. 단, 새 세션에서 코드만으로 재생성되어야 한다. |
| RAG 검색·리랭킹 구성 | **자유** | 프롬프트, 검색·리랭킹 등 RAG 구성은 팀 구현 범위다. |
| 패키지 설치 | **가능** | 필요한 패키지 설치는 자유 항목이다. 단, torch 재설치는 금지다. |
| 제출 노트북 구조 | **고정** | 제공된 두 코드 셀만 유지한다. 모든 팀 코드는 1번 셀에 합치고, 2번 셀은 팀 번호 외 수정하지 않는다. |

위 표의 "규정상 가능하다고 해석"은 운영진의 명시 허가와 동의어가 아니다. 비표준 의존성을 도입하기 전에는 아래 질문으로 확인한다.

> 생성 모델 외에 Hugging Face에서 런타임 중 내려받아 **로컬 실행**하는 임베딩 모델과 로컬 리랭커 모델은 자유롭게 사용할 수 있나요? 또한 로컬 FAISS/SQLite/Chroma 같은 인덱스 라이브러리는 허용 범위인가요?

## 3. DB 선택에 대한 팀 권고와 반증 조건

### 권고

현재 코퍼스는 4개 약관, 72개 조문, 약 229개 항 청크다. 따라서 DB를 두지 않고 list/dict 메타데이터, numpy float32 임베딩 행렬, TF-IDF 희소 행렬을 메모리에 유지한다. 밀집 검색은 전수 내적으로 계산한다. 이는 특정 DB를 쓸 수 없어서가 아니라, 작은 코퍼스에서 전수 비교가 더 정확하고 재현 가능한 선택이기 때문이다.

| 선택지 | 사용 조건 | 현 시점 판단 |
| --- | --- | --- |
| NumPy 전수 검색 | 청크 수가 현재처럼 작고 Colab 단일 실행 | **기본 선택** |
| FAISS IndexFlatIP | 이미 의존성이 안정적이고 API 단순화가 필요한 경우 | 가능하지만 이득이 작다. ANN 인덱스는 쓰지 않는다. |
| SQLite | 메타데이터 질의·디버그 편의가 실제 병목인 경우 | 가능하지만 검색 품질·지연시간 이득은 없다. |
| Chroma/Qdrant/원격 벡터 DB | 영속 서버·외부 서비스가 필요한 경우 | 제출 규정 및 재현성 측면에서 제외한다. |

이 권고가 틀렸다고 판단할 반증 조건은 세 가지다. (1) 운영진이 특정 로컬 라이브러리를 요구하거나 금지할 때, (2) 실제 청크 수가 예상보다 훨씬 커 전수 검색이 의미 있는 병목일 때, (3) 공통 러너에서 메모리·초기화 실패가 재현될 때다. 그 전까지 DB 교체는 품질 개선 실험이 아니다.

## 4. 인덱싱 범위: 누락 여부를 검사할 체크포인트

1. **원문·버전** — 네 약관의 문서명, 시행일, 원문 해시, 조문 수를 고정한다. 이전 버전·웹 UI 문구가 섞이지 않아야 한다.
2. **구조 보존** — 조·항·호·정의·단서·예외·참조 조문을 보존한다. 정규화는 공백·유니코드 같은 표현에 한정하고 숫자, 기간, 금지/예외 표현은 변형하지 않는다.
3. **반환 계약 연결** — 모든 검색 청크가 부모 (문서명, 정수 조번호)를 갖는다. 이 값은 retrieved에 그대로 반환할 수 있어야 하며 문서명 오탈자·중복은 허용하지 않는다.
4. **청킹 손실 점검** — 긴 조문을 보조 청크로 나눠도 부모 조문과 항·호의 문맥이 끊기지 않는지, 질문과 관계없는 인접 본문이 생성 근거를 오염시키지 않는지 확인한다.
5. **검색 표현** — 정확한 숫자·법조문 인용·고유명사를 위한 희소 표현과, 일상어-약관어 간격을 줄이는 로컬 밀집 표현을 독립적으로 측정한다. 두 결과를 결합한다면 결합 규칙도 기록한다.
6. **문서 식별** — 거의 같은 조항이 서로 다른 약관에 존재한다. 임베딩 텍스트와 메타데이터에 문서명·조 제목을 포함하고, 문서 언급이 없는 질문에서 하드 필터링으로 정답 문서를 제거하지 않는다.
7. **후보·재정렬** — 후보 깊이, 부모 조 집계, 중복 제거, 문서 다양성, 선택적 로컬 리랭킹을 각각 분리해 검증한다. 모델이 실제 읽지 않은 근거를 retrieved에 넣지 않는다.
8. **무관 질문과 근거 부족** — 최고 점수가 낮을 때 그럴듯한 조문을 억지 인용하지 않는 경로를 설계하고, 생성 모델이 제공 근거 밖의 사실을 보태지 않게 한다.
9. **재현성·성능** — 원문 파싱/임베딩/인덱싱은 초기화 때 한 번만 수행한다. 새 T4 세션에서 데이터·인덱스·모델이 1번 셀만으로 준비되고, 질의마다 재다운로드·재임베딩하지 않아야 한다.

## 5. 공개 연습 채점의 사용 규칙

공개 10문항 연습 채점은 팀당 최대 2회이며, 운영진이 총점·MRR·키팩트 F1·문항별 판정 근거를 제공한다. 이는 검색 결함과 생성 결함을 분리할 수 있는 귀중한 관측값이지만, 실제 예선은 비공개 30문항과 Flash·Pro 두 평가 모델로 다시 채점된다.

| 회차 | 목적 | 변경 원칙 |
| --- | --- | --- |
| 1차 | sparse 기준선의 계약·검색·생성 오류를 분리 | 코드/프롬프트/모델/검색의 현 상태와 실행 로그를 보존한다. |
| 2차 | 단 하나의 일반화 가능한 개선군을 검증 | 예: 하이브리드 검색 또는 근거 제한 프롬프트. 공개 문항별 답·조문번호 하드코딩은 금지한다. |

두 신청 모두 반드시 **2번 셀이 생성한** answers_public_<팀번호>.json 하나만 제출한다. 파일명과 파일 내부 팀 번호가 일치해야 하며, 수동 JSON 생성은 형식 검증과 실제 제출 경로 검증을 동시에 잃게 만든다. 신청 채널은 공개이므로 다른 팀 결과에서 얻은 정답 조문도 결과기에 하드코딩하지 않는다.

## 6. 적대적 검증 질문

- 이 주장 중 운영진 공지가 아니라 팀의 경험칙인 문장이 있는가?
- 로컬 모델 선택을 "허용 확정"처럼 표현한 곳은 없는가?
- 조문을 쪼개면서도 예외·단서·정의와 부모 조문 연결을 잃지 않았는가?
- 다중 정답 문항에서 중복 조항을 한 문서로만 축소하지 않는가?
- 공개 채점의 문항별 피드백을 비공개 문제에 통할 규칙으로 일반화했는가, 아니면 답을 외웠는가?
- 노트북에 세 번째 코드 셀, 외부 파일, 영속 DB, 원격 API 의존성이 남아 있지 않은가?
