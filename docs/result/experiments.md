# 실험 기록 (experiments)

공개 10문항 연습 채점을 **총 6회** 사용할 수 있다. 회차마다 번호를 붙여 관리하며, **한 회차에는 한 가지 변수만 바꾼다** — 두 가지를 동시에 바꾸면 어느 쪽이 효과를 냈는지 설명할 수 없고, 발표 평가의 "실험 설계와 근거"(10점) 항목에서 근거로 쓸 수 없다.

기술 선택의 배경과 이유는 `docs/DECISIONS.md`, 환경 이슈는 `docs/TROUBLESHOOTING.md` 참고.

## 파일 명명 규칙

회차 번호 `N`에 대해:

| 종류 | 경로 |
| --- | --- |
| 결과기 노트북 | `src/result_generator_N.ipynb` |
| 결과기 출력(2번 셀 생성) | `answers_public_14_N.json` |
| 연습 채점 결과 | `docs/hayes/practice_result_14_N.json` |

## 채점 산식

`practice_result_14_1.json`의 `meta.weights`에서 확인된 가중치:

| 지표 | 가중치 | 무엇을 재는가 |
| --- | --- | --- |
| `mrr` | 0.2 | `retrieved`의 정답 조항 순위 (1등이면 1.0, 2등 0.5, …) — **검색 성능** |
| `keyfact_f1` | 0.3 | 답변이 정답 키팩트를 얼마나 담았는지 — **검색 + 생성 복합** |
| `judge` | 0.5 | Gemini가 accuracy·grounding·completeness·clarity 4축으로 채점 — **생성 품질** |

`performance`(속도) 항목은 연습 채점에서 `disabled` 상태였다. 문항당 120초 제한만 넘지 않으면 된다.

## 회차별 적용 방법

### 1회차 — 3B 기준선 ✅ 채점 완료

| 항목 | 내용 |
| --- | --- |
| 결과기 | `src/result_generator_1.ipynb` |
| 생성 모델 | **Qwen2.5-3B-Instruct** (bitsandbytes 4bit NF4) |
| 검색 ① 키워드 | TF-IDF, `analyzer="char_wb"` **글자 2~5-gram** — 형태소 분석기 없이 한국어 조사·어미 변형을 흡수 |
| 검색 ② 의미 | **bge-m3** 임베딩 코사인 유사도 (revision 고정) |
| 융합 | **RRF** (`k=60`, 각 검색기 상위 8개) — 점수 스케일이 달라도 순위만으로 결합 |
| 청킹 | 조 72개 / 항 229개. **항 단위로 검색 → 부모 조로 max 집계**(small-to-big) |
| 채점 결과 | `docs/hayes/practice_result_14_1.json` |

**결과: 총점 83.494**

| 지표 | 값 | 비고 |
| --- | --- | --- |
| MRR | **1.0000** | 10문항 전부 1순위로 정답 조항 검색 — 검색은 만점 |
| keyfact F1 | 0.6006 | |
| judge 평균 | 90.95 | |

**해석:** 검색이 완벽(MRR 1.0)하므로 **남은 개선 여지는 전부 생성 쪽**에 있다. keyfact F1 0.60이 가장 약한 고리이고, 가중치도 0.3으로 두 번째로 크다. 즉 "근거 조항은 정확히 찾았는데 답변이 키팩트를 다 못 담고 있다"는 상태다.

### 2회차 — 7B로 모델만 교체 ⏳ 채점 대기

| 항목 | 내용 |
| --- | --- |
| 결과기 | `src/result_generator_2.ipynb` |
| **변경 요소** | **생성 모델 3B → Qwen2.5-7B-Instruct (이것 하나만)** |
| 고정 조건 | 1회차와 동일 — 임베딩·검색·청킹·프롬프트·양자화 설정·러너 전부 같음 (diff로 검증: 코드 변경은 `GENERATION_MODEL` 한 줄뿐) |
| 채점 결과 | (대기 중) |

**검증 포인트:** 검색 코드가 동일하므로 **MRR은 1.0으로 똑같이 나와야 한다.** 다르게 나오면 모델 효과가 아니라 비결정적 요소가 섞인 것이므로 원인을 찾아야 한다. 실제로 움직일 지표는 `keyfact_f1`, `judge`, 지연시간이다.

### 3~6회차 — 미정

**남은 회차는 4번뿐이므로 무엇에 쓸지 미리 정해두는 게 좋다.** 1회차 결과가 "검색은 만점, 생성이 약점"을 가리키므로 후보는 다음과 같다:

| 후보 | 노리는 지표 | 근거 |
| --- | --- | --- |
| 프롬프트 개선 (키팩트 누락 방지, 다요소 질문 완결성) | keyfact_f1, judge | 가장 약한 고리를 직접 겨냥 |
| `max_new_tokens` 상향 | keyfact_f1 | 열거형 질문(P03·P05·P10)에서 답변이 잘리는지 확인 |
| `retrieved` 개수 조정 (현재 4개) | mrr | 이미 1.0이라 개선 여지 없음 — **우선순위 낮음** |
| 검색 top-k 조정 (프롬프트에 넣는 근거 수) | keyfact_f1, 지연 | 근거가 부족해서 키팩트를 놓치는지 확인 |

> ⚠️ **MRR이 이미 1.0**이므로 검색 쪽 개선(리랭커 추가 등)에 회차를 쓰는 건 낭비다. 남은 4회는 **생성 품질(가중치 0.3 + 0.5 = 0.8)** 에 집중한다.
