## [Colab] 로컬에서 노트북을 고쳐도 Colab에 반영 안 됨

**증상:** `result_generator.ipynb`를 로컬(레포)에서 수정했는데, Colab에서 다시 실행하면 예전 코드가 그대로 돈다. 예: bitsandbytes(fp16, ~15GB 다운로드)로 되돌아가 있어야 할 게 GPTQ-Int4로 바꾼 뒤에도 여전히 15GB를 받음.
**원인:** Colab은 브라우저에 이미 열려있는 노트북과 로컬 파일이 자동 동기화되지 않는다. 로컬에서 파일을 고쳐도, Colab 쪽 커널은 마지막으로 업로드/실행된 셀 내용을 그대로 들고 있다.
**해결:** 코드를 고칠 때마다 ① 최신 `.ipynb`를 다시 업로드(또는 git pull) → ② 런타임 재시작 → ③ 맨 위 셀부터 다시 실행. 재시작 없이 같은 셀을 재실행하기만 하면 예전 상태가 남아있을 수 있다.

## [Colab] ⚠️ 셀 안에서 pip으로 numpy 버전이 바뀌면 세션이 오염된다

**증상:** 1번 셀에서 `from transformers import ...` 할 때
`ImportError: cannot import name '_center' from 'numpy._core.umath'`.
런타임을 재시작하고 다시 실행해도 **매번 똑같이 재현**된다.

**원인:** Colab 커널은 시작 시점에 이미 numpy를 메모리에 로드해 둔다. 그 상태에서 셀이 pip으로 numpy 버전을 바꾸면
- 디스크의 numpy `.py` 파일 → 새 버전
- 메모리에 이미 로드된 컴파일 모듈(`numpy._core.umath`, `.so`) → 커널 시작 때의 옛 버전

이후 `transformers`가 아직 로드되지 않은 `numpy._core.strings`를 새로 import하면, **새 버전 .py가 옛 버전 .so에서 `_center` 심볼을 찾다가 실패**한다.
재시작이 안 통하는 이유는, 재시작해도 같은 셀이 numpy를 다시 바꾸므로 같은 상태가 매번 재현되기 때문이다.

**시도했으나 실패한 것:**
- 런타임 재시작 (원인이 세션 캐시가 아니라 매 실행마다 재현되는 구조라 무의미)
- 설치 후 `pip install --force-reinstall numpy`
- 설치 후 `pip uninstall numpy` → `pip install numpy`
- 설치 명령에 `numpy<2.5` 핀 (2.5.2 → 2.2.6으로 내려가긴 했으나 증상 동일 — 버전이 문제가 아니라 "세션 중 교체" 자체가 문제)

**해결:** **세션 도중 numpy 버전을 바꾸는 설치를 피한다.** 이 프로젝트에서는 `gptqmodel` 설치가 원인이었고, 양자화 패키지를 쓰지 않는 구성(3B fp16)으로 전환해 해소했다. `torch`/`transformers`/`accelerate`는 Colab에 이미 설치돼 있어 추가 설치가 필요 없다.

**주의 — 문제는 "pip install" 자체가 아니다.** `bitsandbytes`는 numpy를 건드리지 않아 정상 설치됐고, 2번 셀의 `fastapi`/`uvicorn` 설치도 문제없다. 금기는 **이미 커널에 로드된 기반 라이브러리(numpy 등)를 교체하는 설치**다.

**gptqmodel을 꼭 써야 한다면 (미해결, 재도전 시 출발점):** 아무것도 설치하지 않은 새 세션에서 `!pip show numpy`로 **Colab 기본 numpy 버전을 먼저 확인**하고, 그 버전을 정확히 핀으로 걸었을 때 gptqmodel이 수용하는지 확인한다. numpy가 전혀 바뀌지 않으면 이 문제는 발생하지 않는다. (우리가 시도한 `numpy<2.5`는 2.5.2 → 2.2.6으로 *바뀌게* 만들었으므로 여전히 증상이 났다. 버전의 높낮이가 아니라 "세션 중 교체" 자체가 원인.)

**대회 규정과의 관계:** 이 오류는 런타임 재시작으로만 풀리는데, 대회는 "새 Colab 세션에서 위→아래로 한 번 실행"을 요구한다. 따라서 재시작이 필요한 상태를 만드는 구성은 제출본에 쓸 수 없다. 새 패키지를 1번 셀에 추가할 때마다 numpy 같은 기반 라이브러리를 갈아치우지 않는지 확인할 것.

## [Colab] 대형 모델 다운로드 속도 편차가 큼 — 단, 채점과는 무관

**증상:** 같은 크기의 파일인데도 실행마다 다운로드 속도가 크게 다르게 나옴 (관측: 7.98MB/s ~ 80.8MB/s). fp16 원본 15.2GB 기준으로 6분에서 30분 이상까지 널뛴다.
**원인:** Colab 네트워크 대역폭이 세션·시간대마다 편차가 크다.
**해결/판단:** **대응할 필요 없다.** 운영진 확인 결과 채점 대상은 **문항당 `/answer` 응답 시간(120초 제한)뿐**이고, 모델 다운로드·로딩은 1번 셀에서 일어나므로 측정되지 않는다.

> ⚠️ **단, 모델은 반드시 1번 셀에서 즉시 로드해야 한다.** `/health`는 모델 상태와 무관하게 200을 반환하므로, 첫 `/answer` 호출 때 지연 로딩하면 다운로드 시간이 **그 문항의 120초 안에 그대로 들어가** 실패한다. 다운로드 시간이 무관한 것은 어디까지나 1번 셀에서 미리 끝냈을 때의 이야기다.

## [Colab] GPTQ 경로는 의존성 모순으로 사용 불가

**증상:** `Qwen2.5-7B-Instruct-GPTQ-Int4` 로딩 시
`ImportError: Found an incompatible version of GPT-QModel. Found version 2.2.0, but only versions >= 7.0.0 are supported`
**원인:** `optimum`은 `gptqmodel>=7.0.0`을 요구하는데, 위 numpy 문제를 피하려고 `numpy==2.0.2`(Colab 기본값)를 고정하면 pip이 numpy를 맞추기 위해 `gptqmodel`을 2.2.0까지 끌어내린다. 세 조건(optimum ↔ gptqmodel 7.x ↔ numpy 고정)이 동시에 성립하지 않는다.
**해결:** GPTQ 경로 폐기, `bitsandbytes` NF4로 전환. 다운로드 용량이 3배가 되지만 위 항목대로 채점과 무관하다.
**교훈:** 버전 핀은 부작용이 있다 — 하나를 고정하면 pip이 나머지를 옛 버전으로 끌어내려 다른 곳에서 터진다. 핀을 거는 대신 **"바뀌면 즉시 알아채는 검사"**를 두는 편이 낫다 (현재 1번 셀의 numpy 검증 코드가 이 방식).
